# 弱网实验报告

验证目标：在真实屏幕采集 + WebRTC 传输下，回答三个问题，并且**分开回答**：

1. 链路变差时，自适应策略实际改变的是什么（编码尺寸 / 帧率 / 码率上限）？
2. 观看者感受到的**端到端延迟**如何变化？
3. 观看者看到的**文字是否仍可辨认**？

最后一节明确说明为什么不用「平均码率」作为观看质量的单一指标。

数据由 `scripts/experiment.mjs` 生成，汇总由 `scripts/report.mjs` 输出。
原始证据在 `evidence/final/`，包含逐秒采样 JSON 与两端同区域的 PNG 裁剪。

---

## 一、实验方法

```
演示素材（真实桌面） → getDisplayMedia 采集 → VP8 编码 → RTCRtpSender
   → TURN 中继（可注入带宽/时延/抖动/丢包） → 观看者解码 → <video>
```

- **演示素材**是自制页面 `public/fixture.html`：左侧是细字代码（12px 等宽、17px 行高、
  行尾密集中文/英文注释），平滑滚动；右侧是两幅持续更新的动态图表（细网格、9-10px 标签）。
  页面左下角有一条**机器可读校准带**（18×3 个 32px 色块，44 bit 载荷）。
- **延迟**由校准带承载的「编码时刻」与观看者本地时钟求差得到，在 `requestVideoFrameCallback`
  中逐帧采样，因此测的是**画面真正呈现**的时刻，不是轮询时刻。20ms 量化粒度。
- **文字可读性**用两端**同一块文本区域**的裁剪图计算两个指标：
  笔画覆盖率（比纸张底色暗 25 以上的像素占比）与 Weber 对比度
  `(纸张 − 2% 分位) / 纸张`；再按裁剪比例反推观看者实际看到的字形高度。
  区域坐标由 harness 用实际采集尺寸换算，因此演示者裁剪与观看者裁剪覆盖的是同一物理区域。
  不使用观看者页面的实时滚动平均做阶段对比：分辨率切换时那个窗口会混入不同档位的样本。
- **链路**通过 TURN 中继的整形接口控制，profile 作用于真实 UDP 转发路径，
  不是修改页面的 JS 变量。

## 二、基线（无损伤）

| 指标 | 数值 |
| --- | --- |
| 实际编码尺寸 | 1920×1080（20 个采样点全部如此，无档位切换） |
| 实际发送帧率 | 中位数 15.0 fps（内容为滚动 + 图表） |
| 实际发送码率 | 中位数约 4.0 Mbps，峰值 5.0 Mbps（1080p 档上限 5000 kbps） |
| 端到端延迟 p50 / p95 | 346 / 422 ms（5 秒滑动窗口的 p50、p95 各自取中位） |
| 文本区域字形高度 | 12.0 px（1920px 帧下 12px 代码字体的原尺寸） |
| 文本区域对比度 | 0.50（Weber 对比度，同一裁剪区域内自比） |
| 笔画覆盖率 | 7.9% |
| 校准带解码成功率 | 100% |

基线说明：即使链路充裕，帧率也不是 60fps。这是**故意的**——普通软件操作演示
不需要 60fps，降低帧率能换来更高分辨率/更低码率，使文字更清晰。
只有检测到画面大范围变化时才提高帧率（见下节）。

基线必须先**稳定**再测。本轮基线场景显式把中继整形到 25 Mbps / 5ms，
并要求档位连续 4 秒不变、且不在试探中，才开始采样。原因是：不整形时
本地回环的带宽估计在 4–6 Mbps 之间游走，正好卡在 1080p 档 5000 kbps 的上限附近，
档位会在 1080p 与 900p 之间来回——那样采到的「基线」其实是一个瞬态。
（对照：第四节 `healthy` 阶段给的是 6 Mbps，就明显不够撑住 1080p，
12 个采样点里后 4 个落在 900p。这不是缺陷，而是 5000 kbps 上限与 6 Mbps
链路之间的正常余量关系。）

基线延迟必须用**窗口值**读。观看者页面的实时面板保留整场样本（这是给现场观众看的，
数字稳定不跳动），但整场分布会横跨整场网络历史：一次 300 kbps 塌缩之后，
后面的健康阶段仍然会报出塌缩期的 p95，因为数组里还留着几千个旧样本。
因此下面各阶段的延迟统一取观看者「最近 5 秒」的样本，并跳过每阶段开头 6 秒，
避免窗口还探回上一阶段。这也是为什么本报告不引用 `latencySummary` 里的整场数字。

## 三、静止文字 vs 快速动画（不同策略）

| 内容 | 目标帧率 | 实测发送帧率 | 实测变化面积 |
| --- | --- | --- | --- |
| 静止文本（停止滚动、图表降到 1Hz） | 2 fps | 2.0 fps | 中位数 5.9%（4.9–6.4%） |
| 快速滚动 + 12Hz 图表 | 15 fps | 15.0 fps | 中位数 33.1%（25.6–33.8%） |

判定依据是**画面中真正发生变化的面积占比**：把采集画面缩到 320×180，
切成 16×9 网格，与约 750ms 前的参考帧逐格比较，luma 平均变化超过 0.010
的格子算作「在动」，返回运动格占全部格子的比例。

- 静止文档仍有约 **5–6%** 的面积在变（时钟、光标、校准带、图表低频刷新），
  所以静止阈值必须高于这个噪声底；本轮实测静止阶段的中位数为 5.9%。
- 平滑滚动会让约 **1/3** 的格子变化（本轮实测中位数 33.1%），进入中档；
  全屏动画才会超过 70%。
- 由于静止噪声底已经接近中档下部阈值，阈值之间留出了明确间隔：
  升到 15fps 需要变化面积 > 12%，5.9% 的静止读数远低于它；
  升到 30fps 需要 > 42%，实测滚动 33% 仍留在 15fps 档；
  回落则需要低于 9% / 34%（下行阈值更低，形成滞回）。
  之前的实现会在 15/30 fps 之间每秒翻转，加入滞回后目标帧率稳定。
- 参考帧取 750ms 之前而不是上一帧：缩小后几十毫秒的相邻帧位移不足一个像素，
  慢速滚动会被误判为静止。320×180 的分辨率同样是为了保住水平细节。

关键点：**这个决策改变的是发送端 `maxFramerate` 与轨道 `frameRate` 约束**，
不是网页预览的显示尺寸。

## 四、带宽塌缩与恢复（重点）

场景序列：健康 6 Mbps → 塌缩到 300 kbps（含 1% 丢包、60ms 延迟、25ms 抖动）
→ 恢复到 700 kbps → 恢复到 4 Mbps → 1200 kbps + 3% 丢包 + 40ms 抖动。
每个场景开始前先 `/reset` 中继整形，避免上一轮残留的 profile 影响建连时的
带宽估计（这一点在调试中真实踩到过：中断的实验把 250 kbps 留在中继上，
下一场从最低档起步，看起来像自适应失灵）。

由 `node scripts/report.mjs evidence/final` 输出的实际数据（每次运行都会有波动，
表格可由该命令从 `evidence/final/*.json` 重新生成）：

```text
## weak network
  phase           ladder                 encoded sizes                  lat p50/p95     fps
  healthy        1080p -> 900p         1920x1080 1600x900             295/550 ms        14.8
  collapse-300k  900p -> 360p          1600x900 1920x1080 896x504 640x360 4469/8285 ms       4.0
  recover-700k   360p -> 360p          640x360 768x432                505/585 ms        15.0
  recover-4000k  360p -> 504p          768x432 640x360 896x504 1024x576 286/306 ms        15.0
  lossy-1200k    504p -> 360p          1024x576 896x504 768x432 640x360 365/388 ms        15.0
  lat = median of per-second 5 s trailing windows, first 6 s of each phase
  skipped so the window does not reach into the previous phase.

  rung changes (deduped):
    + 53s  360p -> 432p  est=981 kbps  probe (estimate-rose)
    + 73s  432p -> 504p  est=991 kbps  probe (estimate-rose)
```

这张表只放**链路与决策**（档位、实际编码尺寸、延迟、帧率）。文字可读性
**故意不放在这里**：观看者页面的实时锐度是滚动平均，一旦发生分辨率切换，
窗口里会同时混入 1080p 与 360p 的样本，在低档位反而可能算得更高——
那正是本报告要避免的误导性数字。逐阶段可读性见第七节的同区域裁剪表。

### 观察 1：下降快，上升慢

- 塌缩阶段（表中 `collapse-300k`）在十来秒内从 900p 降到 360p，且是**跨档**下降：
  事件日志依次是 `+8s 900p` → `+19s 504p` → `+21s 360p(下限)`，
  严重拥塞时一次跨多档，因此能很快止血。代价是恢复要从最低档重新爬。
  该阶段的 `encoded sizes` 里出现 1920×1080，是 `+12s` 试探 1080p 时短暂的编码尺寸，
  它在 `+18s` 被拥塞信号当场打回（`probe-failed … 已回退`）——
  试探机制在链路已经变差时同样会生效，这正是它要防的场景。
- 恢复阶段（表中 `recover-4000k`，从第 39 秒开始，共 48 秒）不是一步到位：
  360p → 432p（+53s）→ 504p（+73s），**相邻升档间隔约 20 秒**，
  且两次都经过显式的 8 秒试探窗口才提交。此后 `+84s` 又发起了一次
  576p 试探，再次被拥塞信号打回，随即在 `+93s` 降到 432p、`+97s` 到 360p
  ——恢复期里试探失败会自己收手，而不是先拥塞再降下来。
- 表里 `fps` 一列在塌缩阶段只有 4.0，是编码器在极低码率下主动限帧的结果，
  不是测量错误。

### 观察 2：为什么需要「试探」，以及它如何避免再次拥塞

纯粹的「带宽估计 > 当前档位 × 余量」有一个死锁：

> 发送上限被压到 360p 后，编码器只会产生 200–400 kbps 的流量。
> 传输层拥塞控制只能测到它实际看到的流量，于是估计值永远停留在 360p 附近，
> 再也不可能升上去——即使链路早已恢复到 4 Mbps。

解决办法是**有界试探**：临时把编码参数设成上一档（分辨率 + 码率上限都提高），
观察一个窗口（8 秒）：

- 若窗口内出现持续拥塞信号（发送队列 >400ms、丢帧 >8%、**接收端反馈的丢包率 >10%**），
  立即回退，并对下次试探做指数退避（最长 60 秒）。
- 若估计值升到目标档位码率上限的 95% 以上，则提交升档。本轮两次成功的试探都以
  `estimate-rose` 结束：+53s 时 981 kbps 对 432p 的 719 kbps 上限（136%），
  +73s 时 991 kbps 对 504p 的 1044 kbps 上限（95%——刚好压线通过，
  说明提交阈值确实是 95% 而不是 100%）。
- 若失败后估计值又明显上涨（>1.6 倍），**立即取消退避**——
  这正是「带宽刚恢复」的场景，不该再等。

这样既不会在带宽刚恢复时直接拉满（每档都要经过试探与观察），
也不会因为一次保守的失败而永久卡在最低档。事件日志里两类失败都出现过：
`试探后带宽未上升`（保守回退，+40s）与 `试探升档引发拥塞`（被真实拥塞打回，+18s、+90s）。

### 观察 3：重传比例不是拥塞

早期版本用「发送端重传包占比 > 12%」判拥塞，结果在本地中继链路上，
即使**接收端丢包为 0**，重传比例也会在 0–20% 之间波动（晚到的 NACK、调度器行为）。
这导致试探永远失败、恢复永远不发生。

修正后，拥塞判据改用**接收端 RTCP 反馈的真实丢包率**
（`remote-inbound-rtp.fractionLost`），重传比例只作为展示。
本轮数据区分得很清楚：健康阶段 12 个样本全为 0（最大 0.4%），
`recover-700k` 全程 0；塌缩阶段 14 个样本里只有 3 个非零，但峰值达 **59.0%**
（中位数仍是 0——拥塞是成阵出现的，这正是为什么判据用瞬时值而不是阶段平均）；
3% 丢包的 `lossy-1200k` 阶段 **14 个样本全部非零**，实测 0.1–13.7%、
中位数 4.3%，因此该阶段末尾回落到 360p。三种链路状况没有混淆。

## 五、清晰度下限与降级提示

- 硬下限是 **640×360**（`MIN_LADDER_INDEX`）。采集与编码在任何情况下都不会低于它。
- 下限验证结果（`floor` 场景，故意把链路压到 250 kbps 并强制最低档）：

```text
min encoded height: 360 (floor 360)   respected: true
viewer: live  decode 640x360  latency p50 1281 p95 1561 (last 5s window)
```

到达下限后，观看者解码尺寸固定在 640×360，12px 代码字体只剩约 4px 字形——
这是硬下限本身决定的，继续降码率也换不回可读性，所以策略选择「不再往下掉」
而不是「把最后一点带宽也拿去换更糊的画面」。

本轮 `floor` 场景的 12 个采样点**全部**编码 640×360，没有一帧低于下限。
同一场景也展示了低码率下的延迟代价：250 kbps / 80ms / 2% 丢包的链路上，
最近 5 秒窗口的 p50 在 1.16–3.94 秒之间，说明「守住清晰度下限」并不能
让延迟变好——两件事必须分开看。

- 到达下限时，演示者端会发出两条提示：
  - `floor`：已降到最低清晰度 360p，仍可继续接收但文字较小
  - `degraded`：可用带宽约 205 kbps，已到最低清晰度，文字可能难以辨认
- 观看者端对应的文字可读性面板会显示锐度下降与提示语，
  但**不会**把画面替换成占位图——仍能看到内容，只是质量明确下降。
  注意这里的「锐度下降」指画面观感，面板上的 Laplacian 数值受下采样影响，
  不随分辨率单调变化；判断可读性请以同区域裁剪图的对比度与字形高度为准。

## 六、生命周期状态（不能让旧画面冒充直播）

| 场景 | 演示者状态 | 观看者状态 | 观看者画面 |
| --- | --- | --- | --- |
| 权限取消 | `permission-denied` | `permission-denied` | 已清空 |
| 共享轨道结束 | `ended` | `ended` | 已清空，提示「直播已结束」 |
| 切换共享源 | `switching-source` | `source-switching` | 已清空，提示「正在切换共享源」 |
| 演示者 socket 掉线 | `signaling-disconnected` | `signal-lost` | 已清空，提示「与服务器断开」 |
| 仍在直播但 1.5s 无新帧 | `live` | `frozen` | 保留最后一帧 + 「画面已暂停更新」角标 |

唯一的例外是 `frozen`：画面保留，但显式盖上角标说明当前不是实时画面。
其余全部把 `video.srcObject` 置空，避免把旧静态帧误认为仍在直播。

> 注：早期版本里，演示者 socket 掉线会被服务端标记为 `ended` 且不带 `from` 字段，
> 观看者据此误判为「等待演示者」——一个看起来无害、实则暗示"演示者只是还没来"的状态。
> 现在终止状态先按 `state` 判定，再考虑有没有 presenter id。

## 七、延迟与文字可读性分开评估

这两项在弱网下**不是同向变化**，因此不能合并成一个数字：

1. **延迟**主要受链路排队影响，并且必须按**同一时间窗**比较。
   本轮 5 秒窗口数据（p50/p95）：
   健康 `295/550 ms` → 塌缩 `4469/8285 ms` → 恢复 700 kbps 后 `505/585 ms`
   → 恢复到 4 Mbps 后 `286/306 ms` → 丢包 1200 kbps 时 `365/388 ms`。
   两个关键点：
   - 塌缩阶段**两项一起爆**，p50 也到了 4.5 秒。这里的堆起来的是中继的发送队列，
     不是分辨率变化本身；队列一排空，即便仍停在 360p，延迟也回到 0.5 秒以内
     （`recover-700k`）。所以「降分辨率会不会加延迟」没有普适答案，
     要看它是否降低了排队。
   - 如果只看整场会话的累计分布，塌缩期几秒的长尾会被此前几百毫秒的健康样本
     稀释掉，p50 看起来仍然「正常」。这正是必须用滑动窗口、并明确标注统计口径的原因。
   具体数值见第四节表格（每阶段取观看者最近 5 秒样本，跳过阶段开头 6 秒）。
2. **文字可读性**主要受**像素密度**影响。同一块文本区域，两端各保存一张裁剪图，
   在裁剪图内部计算指标（两端是前后几秒分别截取的，文字仍在滚动，因此不能逐像素对齐比较）：

```text
  label              frame   viewer crop  glyph  stroke%   contrast  presenter contrast
  baseline            1920px 820x300      12.0px      7.9%      0.50               0.49
  collapse-300k        640px 273x100       4.0px     10.6%      0.26               0.43
  floor-360p           640px 273x100       4.0px     10.6%      0.28               0.51
  lossy-1200k          640px 273x100       4.0px     11.4%      0.32               0.50
  recover-4000k       1024px 437x160       6.4px      8.3%      0.43               0.46
  recover-700k         768px 328x120       4.8px     11.4%      0.36               0.47
  motion-fast         1920px 820x300      12.0px      5.9%      0.49               0.49
  motion-static       1920px 820x300      12.0px      6.9%      0.50               0.50
  states-live         1920px 820x300      12.0px      6.9%      0.47               0.45
```

   三列读法：

   - **frame**：裁剪图反推出的接收视频宽度。裁剪区域是从观看者画面里按比例
     截出来的，所以 273px 宽的裁剪对应 640px 宽的帧，而不是 273px 的流。
   - **glyph**：12px 代码字体观看者实际看到的字形高度。1080p 时 12px、
     504p 时 6.4px、432p 时 4.8px、360p 时 **4px**。字形只有 4px 高时，
     横竖笔画之间没有余量，再高的码率也补不回来。
   - **stroke%**：比纸张底色暗 25 以上的像素占比。它在 360p 反而**升高**
     （7.9% → 10.6–11.4%）——这不是变清楚，而是笔画被糊开、扩散到更多像素上。
     这个数字只能说明「墨还在」，不能说明「还能认字」。
   - **contrast**：裁剪图内部的 Weber 对比度 `(纸张 − 2% 分位) / 纸张`。
     这一列才是可读性的方向：演示者端稳定在 0.43–0.51，观看者从 1080p 的 0.50
     掉到 360p 的 0.26–0.32，504p 回到 0.43、432p 为 0.36。
     注意 `lossy-1200k` 的 0.32 是最终 360p 的读数——该阶段中途曾在 504p，
     但截图时已因丢包降回最低档。

   关键对照：`motion-static` 里两端完全相同（12.0px / 6.9% / 0.50 对 0.50），
   因为该场景是 1920×1080 且几乎没有运动——这反过来证明裁剪与测量流程本身没有偏差，
   低档位的差异确实来自下采样。

换句话说：

- 只看平均码率，会得到「带宽恢复了所以画质恢复了」的错误结论；
- 只看「墨量/锐度」这类覆盖率指标，会在 360p 得到**更高**的数值，得出相反的结论；
- 只报整场累计的延迟中位数，会在塌缩期显示「一切正常」，因为长尾被健康样本稀释；
- 只有把**按窗口统计的延迟分布**、**字形高度**和**裁剪图内对比度**并列，
  才能说明「什么时候还能看清代码、什么时候只能看个大概」。

### 为什么不用平均码率代表观看质量

平均码率是**发送端的成本指标**，不是观看者的体验指标：

- 同样的 1 Mbps，可以是 1080p 静止画面（清晰、省流量），
  也可以是 360p 高频动画（模糊、费流量）。
- 码率上升可能只是因为在传更多无意义的运动，而不是文字更清楚。
- 本实验中，`recover-4000k` 阶段末停在 504p，对比度恢复到 0.43，
  而该阶段的平均码率只有约 0.75 Mbps，明显低于 `healthy` 阶段的 4.06 Mbps——
  文字比 360p 的塌缩阶段清楚得多，但整段平均码率并没有「回到基线」。
  码率不是决定文字清晰度的那个量。
- 反过来，`lossy-1200k` 阶段的平均码率约 0.86 Mbps，却因为持续性丢包触发降档，
  观看者最终停在 360p（字形 4px、对比度 0.32）——比平均码率更低的
  `recover-700k`（0.23 Mbps、432p 试探中、对比度 0.36）可读性反而更差。
  同样的码率区间，不同的可读性。

因此报告用三组独立数据描述观看质量：
**编码尺寸与字形高度（像素密度）**、**端到端延迟分布（p50/p95/max）**、
**同区域裁剪图的对比度与笔画覆盖率**（外加校准带解码成功率作为对照）。
